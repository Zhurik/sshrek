# sshrek — дизайн

Дата: 2026-10-04
Статус: утверждён к реализации

## 1. Зачем

Сейчас выбор ssh-хоста живёт в функции `.zshrc`:

```sh
choose_ssh () {
    server=$(grep '^Host \w' ~/.ssh/config | cut -d ' ' -f 2 | fzf-tmux -p)
    ...
}
```

У неё три проблемы:

1. Нельзя вернуться к последнему хосту, не проходя через выбор в списке.
2. В списке нет ничего, кроме имени: не видно, куда он ведёт и когда ты там был.
3. Ничего не запоминается — список всегда в одном и том же порядке.

`sshrek` закрывает ровно это. Критерий успеха: `choose_ssh` удаляется из `.zshrc` и
больше не вспоминается.

## 2. Границы

**Делаем:** список хостов из `~/.ssh/config`, выбор через внешний fzf, мгновенный
возврат к последнему хосту, история подключений с длительностями, сортировки,
таблица статистики, релизные бинарники.

**Не делаем** (сознательно, это не «потом»):

- проверку доступности хостов (ping, TCP-проба, latency) — статус в этом проекте
  означает историю, а не живое состояние;
- интеграцию с tmux — поведение как у `kubectl`: никакой магии с окнами и панелями;
- собственный TUI-фреймворк — выбор делает fzf;
- управление живыми сессиями (список, kill, переключение);
- правку `~/.ssh/config` — файл читается, никогда не пишется.

## 3. Интерфейс

Модель — `kubectx`: голая команда открывает выбор, дефис возвращает к предыдущему.

| Команда | Поведение |
|---|---|
| `sshrek` | открывает пикер; Enter → подключение; Esc → выход с кодом 130, без вывода |
| `sshrek -` | подключение к последнему хосту из истории, без UI |
| `sshrek <host>` | подключение напрямую; есть автодополнение |
| `sshrek <host> -- <args>` | всё после `--` дописывается в командную строку `ssh` |
| `sshrek ls` | таблица истории для человека |
| `sshrek ls --porcelain` | тот же набор данных как TSV без выравнивания, для скриптов и для fzf |
| `sshrek ls --porcelain --picker` | только хосты из конфига, в формате строк пикера; используется в `--bind reload` |
| `sshrek preview <host>` | карточка одного хоста; служебная команда для `--preview` в fzf |
| `sshrek completions <shell>` | скрипт автодополнения (`clap_complete`) |

Флаги сортировки для `sshrek` и `sshrek ls`:

- `--sort=config` (по умолчанию) — порядок объявления в `~/.ssh/config`;
- `--sort=recent` — по времени последнего подключения, свежие сверху;
- `--sort=frequent` — по числу подключений.

Короткие формы: `-r` для `recent`, `-f` для `frequent`.

Глобальный флаг `--verbose`: включает диагностику в stderr (пропущенные строки лога,
полная командная строка пикера и `ssh`). По умолчанию выключен.

Платформа — только Unix (macOS и Linux). Windows не поддерживается: обработка
сигналов и семантика кодов выхода в разделе 8 опираются на POSIX.

### 3.1 Коды выхода

| Код | Значение |
|---|---|
| код `ssh` | подключение состоялось — код прокидывается как есть, чтобы `sshrek host && ...` вёл себя как `ssh host && ...` |
| 0 | успешное выполнение `ls`, `preview`, `completions` |
| 1 | ошибка самого `sshrek` (нет конфига, нет истории, пикер не найден) |
| 130 | выбор отменён (fzf вернул 130) — ничего не печатаем |

### 3.2 Переменные окружения

| Переменная | Дефолт | Зачем |
|---|---|---|
| `SSHREK_PICKER` | `fzf` | команда пикера; строка разбивается как шелл-слова, так что `fzf-tmux -p` работает |
| `SSHREK_PICKER_ARGS` | — | если задана, **полностью заменяет** набор флагов, который `sshrek` передаёт пикеру |
| `SSHREK_SSH_BIN` | `ssh` | чем подключаться; нужна для тестов и для обёрток вроде `mosh` |
| `SSHREK_SSH_CONFIG` | `~/.ssh/config` | откуда брать хосты; нужна для тестов |
| `SSHREK_STATE_DIR` | `$XDG_STATE_HOME/sshrek`, иначе `~/.local/state/sshrek` | где лежит история; нужна для тестов |

Файла конфигурации у `sshrek` нет. Трёх переменных и флагов достаточно; свой формат
конфига — лишняя сущность.

## 4. Архитектура

Поток данных линейный, без обратных связей:

```
~/.ssh/config ──► config::parse ──┐
                                  ├──► sort::apply ──► render ──► picker (fzf) ──► alias
sessions.jsonl ─► history::stats ─┘                                                 │
                                                                                    ▼
                                                              runner: start-событие → spawn ssh
                                                              → wait → end-событие → exit(код ssh)
```

Модули:

| Модуль | Ответственность | Зависит от |
|---|---|---|
| `cli` | описание команд и флагов (clap derive) | — |
| `paths` | где лежат конфиг и состояние, с учётом env и XDG | — |
| `config` | парсинг `~/.ssh/config` → `Vec<HostEntry>` | `paths` |
| `history::event` | типы событий и их сериализация | — |
| `history::store` | append в лог, чтение лога | `paths`, `event` |
| `history::stats` | свёртка событий в `HostStats` | `event` |
| `sort` | три стратегии упорядочивания | `config`, `stats` |
| `render` | строки для пикера, таблица для `ls`, карточка для `preview` | `config`, `stats` |
| `picker` | запуск внешнего пикера, разбор выбранной строки | `render` |
| `runner` | запуск `ssh`, запись сессии, прокидывание кода выхода | `store` |
| `main` | склейка: разбор аргументов → вызов нужного сценария | все |

Правило границ: `render` ничего не знает про fzf (отдаёт строки), `picker` ничего не
знает про историю (принимает готовые строки), `runner` ничего не знает про config
(принимает алиас и аргументы). Каждый модуль тестируется в одиночку.

### 4.1 Типы

```rust
struct HostEntry {
    alias: String,
    hostname: Option<String>,
    user: Option<String>,
    port: Option<u16>,
    order: usize,          // позиция в config, основа сортировки по умолчанию
}

struct HostStats {
    host: String,
    connections: u32,            // число start-событий
    last_connected: Option<DateTime<Utc>>,
    total_duration: Duration,    // сумма закрытых сессий
    last_duration: Option<Duration>,
    failures: u32,               // сессий с ненулевым кодом выхода
    unfinished: u32,             // start без end
}
```

## 5. История

### 5.1 Формат

`$STATE_DIR/sessions.jsonl` — append-only, по одному JSON-объекту на строку:

```json
{"v":1,"event":"start","id":"18f2a9c4e1-4821","host":"potato","at":"2026-10-04T17:08:35Z","args":["-L","8080:localhost:80"]}
{"v":1,"event":"end","id":"18f2a9c4e1-4821","at":"2026-10-04T17:42:01Z","exit":0}
```

Решения и причины:

- **Два события вместо одной записи по завершении.** Если `sshrek` убьют `kill -9`,
  факт подключения всё равно уже в логе — потеряется только длительность. Запись
  «только в конце» потеряла бы и сам факт.
- **`id` = `<unix_nanos в hex>-<pid в hex>`.** Уникален без генератора UUID и без
  лишней зависимости, читается глазами.
- **`v` — версия схемы.** Читатель пропускает строки с неизвестной `v`, так что
  будущее изменение формата не превращает лог в мусор.
- **Append-only, никогда не перезаписывается.** Открытие с `OpenOptions::append`,
  одна запись = один `write` строки, завершённой `\n`.
- **Битые строки пропускаются**, а не роняют программу: при `kill -9` во время
  записи возможна обрезанная строка. Число пропущенных строк печатается в stderr
  только при `--verbose`; в обычном режиме они молча игнорируются.

Файл грепается и правится руками, что для инструмента такого размера важнее любых
индексов.

### 5.2 Агрегация

`history::stats` читает лог построчно и сворачивает в `HashMap<String, HostStats>`:

- `start` → `connections += 1`, обновление `last_connected`, запоминание
  `(id → (host, at))` в словаре открытых сессий;
- `end` → поиск `id` среди открытых; при совпадении считается длительность, пишется
  `total_duration`/`last_duration`, при `exit != 0` растёт `failures`;
- `end` без известного `start` (лог обрезан сверху) игнорируется;
- `start` без `end` по завершении обхода → `unfinished += 1` (активная прямо сейчас
  сессия или прерванная).

Оценка объёма: 16 хостов, 50 подключений в день → ~36 тысяч строк в год, порядка
3 МБ. Полное чтение и свёртка — единицы миллисекунд. Ни индекса, ни кэша не нужно;
если файл когда-нибудь станет неприлично большим, его можно просто обрезать.

«Последний хост» для `sshrek -` — это `host` последнего `start`-события в файле.
Если лога нет или он пуст: `sshrek: истории пока нет, запусти sshrek без аргументов`
и выход с кодом 1.

## 6. Чтение `~/.ssh/config`

Нужен только список алиасов в порядке объявления плюс `HostName`/`User`/`Port` для
карточки. Это ~100 строк собственного парсера; внешний крейт принёс бы полную
семантику ssh-конфига, которая здесь не используется.

Правила:

- ключевые слова регистронезависимы, разделитель — пробелы или `=`;
- `Host foo bar baz` объявляет три алиаса, каждый со своим `order`;
- алиасы с `*`, `?` или ведущим `!` отбрасываются — это паттерны, а не хосты
  (у тебя в конфиге это `Host *`);
- `HostName`, `User`, `Port` подхватываются из блока текущего `Host`;
- блоки `Match` пропускаются целиком: их условия вычисляются в момент подключения,
  и статического списка из них не получить;
- `Include` раскрывается: `~` разворачивается, относительные пути — от `~/.ssh/`,
  поддерживается glob; защита от циклов — множество уже прочитанных файлов и предел
  глубины 16;
- дубликат алиаса (объявлен дважды) берётся по первому вхождению.

Отсутствие `~/.ssh/config` — не паника: пустой список хостов, а `sshrek -` и
`sshrek <host>` продолжают работать.

## 7. Пикер

### 7.1 Строки

Первое поле строки — алиас; он же возвращается из пикера и передаётся в `preview`.
Остальные колонки выравниваются по ширине самого длинного значения:

```
potato    2h ago        42×   root@10.0.0.5
rpi5      3 days ago    11×   pi@192.168.1.5
france    never          0×   france.example.com:2222
```

«never» — хост из конфига, в который ты ещё не заходил. Относительное время считает
своя функция `fmt_relative(then, now)` (секунды → `just now`, минуты, часы, дни,
недели, месяцы) — двадцать строк кода и честный юнит-тест вместо ещё одного крейта.

### 7.2 Запуск

`SSHREK_PICKER` разбирается как шелл-слова (`shell-words`), первое слово — программа,
остальные — её аргументы. Затем дописываются наши флаги (или `SSHREK_PICKER_ARGS`,
если задана):

```
--no-sort --layout=reverse --height=40% --prompt='ssh > '
--preview '<self> preview {1}' --preview-window=right,45%,border-left
--header 'ctrl-o config · ctrl-r recent · ctrl-f frequent'
--bind 'ctrl-o:reload(<self> ls --porcelain --picker --sort=config)'
--bind 'ctrl-r:reload(<self> ls --porcelain --picker --sort=recent)'
--bind 'ctrl-f:reload(<self> ls --porcelain --picker --sort=frequent)'
```

- `--no-sort` сохраняет наш порядок при равном скоринге поиска — без него дефолтная
  сортировка «как в config» потерялась бы.
- `<self>` — путь из `std::env::current_exe()`, экранированный; так `preview` и
  `reload` работают и для бинарника, который не лежит в `PATH`.
- Эти флаги понимает и `fzf-tmux`: неизвестные ему аргументы он передаёт в `fzf`.
  Поэтому `SSHREK_PICKER='fzf-tmux -p'` даёт прежний popup со всеми плюшками.
- Строки идут пикеру в stdin, выбранная строка читается из stdout, берётся первое поле.
- Код 130 от fzf = отмена: выходим с 130 молча. Ненулевой код, кроме 130, —
  сообщение об ошибке и код 1. Отсутствие бинарника пикера — отдельное внятное
  сообщение с подсказкой про `SSHREK_PICKER`.

Флаг `--picker` у `ls --porcelain` означает «только хосты из конфига, формат для
пикера». Без него `ls` показывает всё, включая хосты, которые есть в истории, но
исчезли из конфига (с пометкой), — подключиться к ним нельзя, но знать о них полезно.

## 8. Подключение

```
записать start-событие
  ↓
на время ожидания: SIGINT и SIGQUIT в родителе → SIG_IGN
  ↓
spawn SSHREK_SSH_BIN <alias> <extra args...>, stdio наследуется
  ↓
wait
  ↓
записать end-событие (время, код выхода)
  ↓
exit(код ssh); если ssh убит сигналом N → exit(128 + N)
```

Почему `spawn` + `wait`, а не `exec`: без ожидания завершения не будет ни
длительностей, ни кодов выхода, то есть не будет истории событий. Цена — лишний
процесс в дереве; для интерактивного инструмента это незаметно.

Почему игнорировать SIGINT в родителе: Ctrl-C летит всей foreground-группе. Если
`sshrek` умрёт от него первым, `end`-событие не запишется и сессия навсегда
останется «незавершённой». `ssh` свой SIGINT получит сам, так что поведение для
пользователя не меняется.

`stdin`/`stdout`/`stderr` наследуются без изменений — иначе сломаются TTY, raw-режим,
проброс ключей и всё интерактивное.

Если `ssh` не удалось запустить (нет бинарника, нет прав) — сообщение
`sshrek: не удалось запустить 'ssh' (см. SSHREK_SSH_BIN)` и код 1. `start`-событие
уже в логе, поэтому сразу за ним пишется `end` с `"exit": null` и полем `"error"`:

```json
{"v":1,"event":"end","id":"18f2a9c4e1-4821","at":"2026-10-04T17:08:35Z","exit":null,"error":"no such file or directory"}
```

В агрегации такое событие закрывает сессию с нулевой длительностью и увеличивает
`failures` — как и любой ненулевой код выхода.

## 9. Сортировки

```rust
enum SortKey { Config, Recent, Frequent }
```

- `Config` — по `HostEntry::order`.
- `Recent` — `last_connected` по убыванию; хосты без истории уходят в конец и между
  собой упорядочены по `order`.
- `Frequent` — `connections` по убыванию, при равенстве `last_connected` по
  убыванию, затем `order`.

Все три — полные порядки без ничьих, так что вывод детерминирован и его можно
проверять в тестах построчно. Frecency-формул сознательно нет: порядок должен быть
предсказуемым, а не «умным».

## 10. Ошибки

`anyhow` с контекстами по всему коду: иерархия своих типов ошибок для инструмента
такого размера не оправдана. Правила:

- все сообщения в stderr, с префиксом `sshrek: `, на одной строке, без backtrace;
- история никогда не причина падения: если лог не читается или не пишется,
  печатается предупреждение, а подключение всё равно происходит — инструмент в
  первую очередь должен подключать;
- каталог состояния создаётся лениво, при первой записи.

## 11. Тестирование

TDD: тест до реализации, по одному поведению за раз.

**Юнит-тесты** (чистые функции, без ввода-вывода):

- `config`: несколько алиасов в одной строке; `=` как разделитель; регистр ключевых
  слов; отбрасывание `Host *` и паттернов; `Include` с glob и `~`; цикл во
  `Include`; пропуск блока `Match`; дубликат алиаса; отсутствие файла.
- `history::stats`: пара start/end; start без end; end без start; битая строка
  посреди лога; неизвестная `v`; подсчёт `failures`; суммирование длительностей.
- `sort`: все три стратегии, включая хосты без истории и равные значения.
- `render`: выравнивание колонок; `fmt_relative` на границах (59 с, 60 с, 23 ч, 24 ч,
  6 дней, 7 дней); `never` без истории.

**Интеграционные тесты** (`assert_cmd` + `tempfile`), на подменённом окружении:
`SSHREK_STATE_DIR` в temp-каталог, `SSHREK_SSH_CONFIG` на фикстуру,
`SSHREK_SSH_BIN` на скрипт-заглушку, `SSHREK_PICKER` на заглушку, печатающую
нужную строку.

- `sshrek <host>` пишет в лог start и end и возвращает код заглушки;
- `sshrek -` подключается к хосту из последнего start-события;
- `sshrek -` без истории: код 1 и внятное сообщение;
- отмена в пикере (заглушка с кодом 130): код 130 и пустой stdout;
- `sshrek ls --porcelain` даёт стабильный TSV;
- `sshrek ls` на пустой истории не падает;
- недоступный для записи `STATE_DIR`: предупреждение, но подключение состоялось.

Именно ради этих тестов все внешние точки (ssh, пикер, пути) берутся из env —
тестируемость здесь причина дизайна, а не следствие.

| Крейт | Зачем |

## 13. CI и релизы

### 13.1 `.github/workflows/ci.yml`

На push и pull request: `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`,
`cargo test` на `ubuntu-latest` и `macos-latest`. Кэш — `Swatinem/rust-cache`.

### 13.2 `.github/workflows/release.yml`

Триггер — push тега вида `v[0-9]+.[0-9]+.[0-9]+*` (semver, с опциональным
pre-release суффиксом).

**Job `verify`:** версия в теге совпадает с `version` в `Cargo.toml`, иначе релиз
падает сразу. Это дешёвая защита от тега, который никому не соответствует.

**Job `build`,** матрица из четырёх целей:

| runner | target | примечание |
|---|---|---|
| `ubuntu-latest` | `x86_64-unknown-linux-musl` | `musl-tools` из apt |
| `ubuntu-24.04-arm` | `aarch64-unknown-linux-musl` | нативный arm-раннер, без кросс-компиляции |
| `macos-13` | `x86_64-apple-darwin` | Intel-раннер |
| `macos-latest` | `aarch64-apple-darwin` | Apple Silicon |

Linux собирается под musl, а не gnu: C-зависимостей нет, поэтому бинарник выходит
полностью статическим и запускается на любом дистрибутиве независимо от версии glibc.

Каждая задача: `rustup target add`, `cargo build --release --target <target>`,
упаковка в `sshrek-<tag>-<target>.tar.gz` (бинарник, `README.md`, `LICENSE`) и
`.sha256` рядом, выгрузка артефакта.

**Job `release`:** собирает артефакты, склеивает `SHA256SUMS`, публикует через
`softprops/action-gh-release@v2` с `generate_release_notes: true`; `prerelease: true`,
если в теге есть `-`. Права — `contents: write`, остальное по минимуму.

Выпуск версии: поднять `version` в `Cargo.toml` → коммит → `git tag vX.Y.Z` → push
тега. `cargo-dist` не берём: четыре явных шага в workflow читаются и правятся без
изучения отдельного инструмента.
